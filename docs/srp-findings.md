# SRP: что мешает внешним TUI и что стоило бы изменить в Som

Записано по ходу встраивания SRP во вьюер farsh (F3, Ctrl+Q). Это наблюдения
о том, что пришлось копировать или обходить; решать в Som, не здесь.
Статус каждого пункта: **факт** (проверено в коде или тестом) или
**гипотеза** (ещё не проверено в Som живьём).

## 1. Клиенту нужен лёгкий общий крейт (факт)

Чтобы показать картинку, внешнему клиенту (farsh, yazi) пришлось
скопировать: типы сообщений (`SrvRequest::PutChunk`, `HandshakeInfo`,
`ContentType`, `ContentMetadata`, `ConnectionKind`), кадры канала
(u32 LE длина + JSON) с Windows-вариантом на overlapped I/O (~90 строк) и
таблицу из 297 диакритиков placeholder'а. Всё это живёт в `somsrv` и
`terminal`, которые тянут alacritty_terminal, mlua, gpui, theme, settings.

yazi уже сделал такую копию и отстал (`som_srv`, `somcat`). farsh сделал
вторую. Две копии разойдутся.

**Предложение:** крейт `srp_client` в som без зависимостей Zed
(serde, serde_json, libc / windows-sys). В него переезжают `protocol`
(типы), `pipe`, `kitty_graphics_placeholder`, часть `srv_channel`.
`somsrv`, `terminal`, `somsrp` берут их оттуда. Внешние клиенты берут
крейт git-зависимостью с закреплённым rev.

## 2. Рукопожатие содержит то, что клиенту не нужно (факт)

`HandshakeInfo { version, os, arch, build_id, pid }` нужен реле для
решения «обновить ли демон». Для `Srv`-соединения демон его только
логирует и отвечает своим (`server.rs`, `handle_srv`). Внешний клиент
вынужден придумывать `version` и `build_id`.

**Предложение:** для `Srv`-клиента отдельное лёгкое приветствие
(`ClientHello { name, version }` или вовсе без полей) либо `#[serde(default)]`
на `version`/`build_id`, чтобы клиенту хватало `os`/`arch`.

## 3. `PutChunk.data` как JSON-массив чисел (факт)

`data: Vec<u8>` сериализуется как `[7,8,...]`: в среднем 3-4 байта JSON на
байт файла. Для картинки в 5 МБ это ~18 МБ JSON, который демон разбирает
обратно. Видео и аудио идут тем же путём.

**Предложение:** `#[serde(with = "serde_bytes")]` (или base64) для `data`
либо бинарный кадр для `PutChunk` (признак типа в первом байте, затем
заголовок и сырые байты). Это совместимо, если версии согласуются через
`HandshakeInfo`.

## 4. Цвет подчёркивания (SGR 58) несёт `file_id` (факт)

Ячейка placeholder'а: fg = session_id, цвет подчёркивания = file_id.
Модель ячейки ratatui/crossterm поддерживает underline color только
недавно и не везде; в farsh пришлось добавить поле в `Cell` и вручную
печатать `ESC[58;2;r;g;bm`. Ещё одна нетривиальная вещь для каждого
фреймворка.

**Предложение:** допускать кодирование `file_id` без SGR 58, например:
fg = session_id, а `file_id` в bg, или (как в самом Kitty, где третий
диакритик после строки и столбца несёт старший байт id) id в диакритиках.
Старый способ оставить как есть.

## 5. «Мы в Som» узнаётся только по переменной окружения (факт)

`SOM_WINDOW_ID` Som ставит при локальном запуске и в своих ssh-вкладках
(по руководству). Через обычный `ssh` из чужого терминала переменная не
доходит, а `sudo`/`env -i`, скорее всего, её сбросят (гипотеза). Других
способов нет: ни ответа на `XTVERSION`/DA, ни OSC-запроса.

**Предложение:** ответ Som на `CSI > q` (XTVERSION) строкой `som <версия>`
и/или OSC-запрос возможностей (`OSC 1337 ; Capabilities`). Тогда клиент
может спросить терминал, а не гадать по окружению. В ConPTY ответ приходит
нажатиями клавиш, это надо учесть (farsh без панелей отдаёт ввод шеллу
как есть; запрос надо делать до запуска шелла).

## 6. Нужен ли пиксельный размер ячейки? (факт)

В руководстве есть раздел «Sizing the placement: real terminal cell
metrics» и `CSI 16 t`. Som вписывает картинку в прямоугольник placement'а
сам, с сохранением пропорций (`terminal_element.rs`), поэтому клиенту
достаточно отдать весь прямоугольник. farsh размер ячейки не запрашивает.
В руководстве стоит прямо сказать, что для картинок это не требуется;
сейчас раздел заставляет клиента делать лишний запрос (на Windows через
ConPTY ответ приходит как клавиши).

## 7. Демон: запускать или нет (факт, обсуждаемо)

Руководство предлагает клиенту запустить `somsrv`, если он не работает,
и искать его рядом со своим exe. Для farsh это опасно: «новый somsrv рядом
убивает сессии», а farsh живёт внутри сессии. farsh только подключается к
работающему демону.

**Предложение:** написать в руководстве явно, что клиент внутри сессии Som
не запускает и не заменяет демон; либо дать в демоне команду «запущен ли
ты» (`--ping`), чтобы клиент мог проверить без подключения.

## 8. Som забирает клавиши и мышь над виджетом (гипотеза, из чтения кода)

`handle_audio_widget_key`: Space и стрелки у плейлиста берёт Som, пока на
экране виджет «now playing». Quick view в farsh показывает виджет рядом с
командной строкой, где нужен пробел. Чтобы это работало, Som должен
отдавать клавиши виджету только у верхнего (полноэкранного) placement'а
или только когда у него фокус по клику.

## 9. Ресайз переписывает ячейки placement'а (гипотеза)

`resync_rich_content_placements` на ресайзе сам переписывает ячейки и
может вставлять или удалять строки (основной и альтернативный экран не
различаются). Клиент, который рисует placement позиционированием
курсора на альтернативном экране (farsh), ждёт, что ячейки останутся, как
он их нарисовал. Проверяется живым тестом.

## 10. Нет способа отозвать placement, кроме как стереть ячейки (факт)

`EndPlayback` идёт от Som к клиенту, а `StopPlayback` от клиента к Som
остановит аудио/видео, но для картинки нет «убрать placement, я закрыл
вьюер»: кэш живёт, пока его не вытеснит демон. Для quick view, где файл
меняется на каждое движение курсора, это лишние записи в кэше.

**Предложение:** `SrvRequest::Release { session_id, file_id }`, после
которого демон сразу освобождает запись.

## 11. Живой тест фазы 1 в Som (2026-11-06, факт)

Картинки png, jpg, gif в F3 и в quick view (Ctrl+Q) Som рисует из ячеек
farsh на альтернативном экране, вписывая с сохранением пропорций; смена
файла в quick view обновляет картинку. Гипотеза 9 (ресайз) частично:
placement перерисовывается правильно, но после изменения размера окна
farsh ConPTY не прислал запись о ресайзе: экран оставался в старом размере
до первой клавиши. Это не вина SRP; в farsh добавлен опрос
`terminal::size()` в цикле панелей. Что Som делает с PTY при ресайзе
(не шлёт запись `WINDOW_BUFFER_SIZE_EVENT`?), стоит проверить в Som.

## 12. Живой тест аудио (2026-11-06, факт)

mp3 в F3 и Ctrl+Q: виджет Som с тегами (название, исполнитель, альбом, год),
обложкой, длительностью и полосой прогресса; воспроизведение идёт за пределы
первых 256 КБ, перемотка кликом по полосе отрабатывает (запросы диапазонов
обслуживает второе соединение farsh). Наблюдения для Som: (а) в Quick view
игра начинается сама, как только курсор остановился на файле; клиент не может
показать «плеер без автозапуска», нужен флаг в метаданных или `AnnounceTrack`
(`autoplay: false`); (б) теги и обложка приходят позже названия, виджет
сначала показывает только имя файла.

## 13. Живой тест .m3u и .cue (2026-11-06, факт)

Список из двух треков: старт, `n`, `p` и кнопки виджета переключают треки, у
каждого трека новое размещение (farsh меняет цвета ячеек, вьюер сам
перерисовывается). `.cue` с тремя треками и одним flac: виджет показывает
«1. First», исполнителя, альбом, год. Наблюдение для Som: у размещения с
CUE кнопка «следующий» ведёт себя как переход по трекам внутри файла, а не
по списку farsh; клиент не может отличить, что нажато, пока Som не пришлёт
PlaylistStep (он приходит только для списка).

## 14. Живой тест .md (2026-11-06, факт; причины — гипотезы)

Документ рисуется Som в F3 и в Ctrl+Q, прокрутка окном строк размещения
(PgUp/PgDn/стрелки/колесо/Home/End) работает. Что мешает внешним TUI:
(а) Som рисует документ поверх всего ниже первой ячейки, а не только поверх
своих ячеек: в Ctrl+Q текст закрывает нижнюю рамку панели и часть
клавиатурной строки, в F3 пришлось убрать заголовок и строку состояния;
Som должен обрезать рисование документа по видимым ячейкам размещения, как
для картинок;
(б) у документа свой скролл в Som (Scroll Lock и колесо), независимый от
строк ячеек; клиент не знает, какой из двух сработает;
(в) последние ~5 строк документа из 12 разделов недоступны: сумма строк по
`GrowMarkdownRows` меньше, чем Som рисует (гипотеза: строки считаются по
высоте ячейки, заголовки выше); конец документа нельзя показать, пока Som не
присылает полное число строк или не обрезает рисование;
(г) таблица в Markdown выводится слитно («ab12»), это отрисовка Som, не
farsh;
(д) ресайз с документом проверен: Som перекладывает текст под новую ширину;
если farsh не получил запись о ресайзе, экран не обновлялся (в farsh
добавлен опрос размера). Выбор дорожек `a`/`s` + цифра для видео проверен:
видео перезапускается, неверный номер не роняет проигрыватель; список
дорожек клиенту взять негде, а в виджете Som выбора дорожки нет — стоило бы
добавить его в виджет, чтобы клиентам не нужно было знать номера.

## 15. Радио (2026-11-06, факт)

Радио (`yandex:wave` в `.m3u`) перенесено из somsrp. Заметка о тестировании:
тестовый `somsrv`, собранный из сборки пользователя
(`SOMSRV_INSTANCE=farshtest`), использует ту же привязку аккаунта Яндекса, что
и демон пользователя: радио на нём не «падает» как на чистом, а играет и шлёт
`RadioFeedback` настоящему аккаунту. Для тестов клиентам нужен демон без
привязки (например, отдельная папка данных через переменную окружения) либо
поддельный сервис.
